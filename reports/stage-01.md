# Этап 1: модели данных и Django Admin

## Что сделал

1. Разбил backend на три приложения: `catalog` (категории, товары, теги, отзывы, скидки, настройки магазина), `orders` (заказы, позиции заказа, оплата), `accounts` (профиль пользователя).
2. Спроектировал и создал модели по контракту `swagger.yaml`: `Category` (с самоссылкой для подкатегорий), `Tag`, `Product`, `ProductImage`, `Specification`, `Review`, `Sale`, `ShopSettings`, `Order`, `OrderItem`, `Payment`, `Profile`.
3. Реализовал мягкое удаление товаров: поле `is_deleted` плюс два менеджера — `objects` отдаёт только активные записи, `all_objects` возвращает всё. В админке переопределил удаление (единичное и массовое), чтобы оно ставило флаг вместо реального `DELETE`, добавил действие «Восстановить».
4. Настроил автоматический пересчёт рейтинга товара сигналом на добавление/удаление отзыва — не считаю `AVG()` при каждом обращении к каталогу.
5. Сделал data-миграцию, создающую группы `Администратор` и `Покупатель` (`django.contrib.auth.Group`) — под них в Этапе 2 настрою права на конкретные действия.
6. Написал management-команду `seed_demo`, наполняющую базу демоданными (идемпотентна), и выгрузил результат в фикстуру `fixtures/demo_data.json`: администратор, два покупателя с паролем `123456`, 7 категорий, 5 тегов, 12 товаров, отзывы, скидки, демо-заказ с оплатой.
7. Настроил Django Admin для всех моделей: список с нужными колонками, фильтры, поиск, inline-формы (изображения и характеристики товара — прямо на странице товара; позиции заказа и оплата — на странице заказа).
8. Проверил всё в браузере вживую: вход в админку, списки, карточка товара с инлайнами, работу фильтров и автоподсчёта рейтинга.

## Для чего

Этап должен дать полную модель данных магазина и рабочую админку, чтобы на Этапе 2 оставалось только описать API поверх готовых моделей — без изменения структуры БД на ходу.

## Почему именно так

- Мягкое удаление — стандартная практика для интернет-магазина: удалённый товар мог быть в чьих-то старых заказах, реальное удаление строки сломало бы историю покупок.
- Рейтинг храню как поле, а не считаю на лету — при листинге каталога с сортировкой по рейтингу это будет один из немногих полей, которые запрашиваются на каждой странице, а `AVG()` по отзывам на каждый запрос — лишняя нагрузка.
- `/banners`, `/products/limited`, `/products/popular` в `swagger.yaml` возвращают одну и ту же схему `Products` — то есть это три выборки товаров, а не категорий. `is_banner` и `is_limited` сделал явными флагами (это осознанный выбор администратора), а `popular` — вычисляемой выборкой (топ по рейтингу), потому что по смыслу это не то, что должен вручную отмечать администратор.
- Роли делаю через стандартные `django.contrib.auth.Group`, без отдельной модели роли — этого достаточно для двух ролей из ТЗ и не плодит лишних сущностей.
- Демоданные оформил как management-команду, а не как часть data-миграции — это тестовые данные, а не часть схемы БД, и команду можно перезапускать и менять отдельно от миграций.
